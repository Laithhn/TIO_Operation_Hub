# TIO Operations Hub — UI/UX and QA Audit

**Audit date:** 27 October 2026  
**Application commit:** `fbbb3e36ad16d0c6ab554329383034eaa04026f3`  
**Environment:** Windows, local Development application, Microsoft Edge via Playwright, isolated LocalDB instance `TioHubQALocalDB`  
**Audit type:** Automated end-to-end and backend suite, source/design review, and responsive visual inspection. No representative-user study was performed.

## A. Executive summary

The main operational flows are functionally reliable in the tested local environment: the .NET suite passed 246/246, and all 72 Playwright tests passed. The most important observed UX problems are concentrated in narrow layouts. At 360–390 px the global top navigation clips its active item and provides no obvious scroll cue; wide operational tables remain horizontally scrollable inside the content region and some values/actions are cut off until the user discovers that scroll region. The page itself does not grow wider than the viewport in the six sampled breakpoints.

The application has several strong interaction foundations: role-aware navigation, search and keyboard access, filters/sort/pagination/export, validation, confirmation for destructive actions, stale-edit handling, and successful create/edit/approval/report journeys. These are supported by test evidence. The audit did not test with actual staff, assistive technology, production identity, non-Edge browsers, or a production-scale dataset. Scores below are provisional expert-review ratings, not measured user outcomes or a compliance certification.

**Immediate actions:** improve mobile navigation affordance; provide a narrow-screen presentation for wide tables; measure and tune loading performance because the production build emits a large JavaScript chunk; conduct a screen-reader and contrast review before asserting WCAG 2.2 AA conformance.

## D. Detailed findings register

### UX-001 — Narrow header navigation clips labels without a clear affordance

| Field | Finding |
|---|---|
| Module / screen | Shared shell; all pages, observed on Cases, Dashboard and Reporting Center at 360–390 px and on tablet at 768 px. |
| Category / title | Navigation — Global navigation labels are clipped on narrow screens. |
| Current behavior | The top navigation shows a partial “Dashboard” label at 360 px; at 768 px the next section label is cut off. The region can overflow internally, but the screenshot provides no clear visual cue that additional destinations are available by horizontal scrolling. The hamburger opens a separate section menu. |
| Expected behavior | Users can identify the current section and discover all available sections at narrow widths without guessing or relying on an unexplained horizontal gesture. |
| Reproduction steps | Open `/cases` or `/` at 360×800 or `/reports` at 390×844; inspect the top bar. At 768×1024 inspect the primary section labels. |
| Severity / priority | Medium / P1 for tablet/mobile operational use; P2 if those widths are outside the supported use case. |
| User and business impact | Users may miss a section or spend time trying to pan the header; this increases navigation effort and makes the global shell appear broken. |
| Root cause | Verified layout behavior; likely the fixed horizontal navigation arrangement has insufficient narrow-width adaptation. Underlying component cause is a hypothesis pending CSS inspection. |
| Recommended solution / proposed design | At narrow breakpoints, replace the clipped strip with a compact active-section control or a clearly scrollable tab row with edge fades/chevrons and keyboard support. Keep the section drawer as the complete navigation list and visibly indicate the active section. |
| Acceptance criteria | At 360, 390 and 768 px, current section text is fully visible; every section is reachable by keyboard and touch; any horizontal scroll is signposted; no header control overlaps search/notifications/profile; focus remains visible. |
| Effort | Medium. |
| Evidence | Responsive captures: `360-cases.png`, `360-dashboard.png`, `390-reports.png`, `768-clients.png` under `C:\Users\lmh\AppData\Local\Temp\tiohub-ux-review`. No document-level overflow was measured. |
| Verification status | Verified. |

### UX-002 — Operational tables hide secondary columns behind an undiscoverable scroll region

| Field | Finding |
|---|---|
| Module / screen | Clients, Cases, Settings and other wide lists; captured Clients, Cases and Settings at 360–390 px, with representative routes across all responsive widths. |
| Category / title | Responsive data presentation — Wide tables require horizontal scrolling on mobile. |
| Current behavior | The viewport itself stays within the device width, but main-content scroll width is greater than the viewport (for example, 481 px on narrow client/case/settings content; 529 px on the dashboard; 599 px on reports). At 360 px, the Settings table exposes a horizontal scrollbar near the bottom of a large table area; in the client list, names/columns are clipped until the table is panned. No card or row-detail mode is present in the observed viewport. |
| Expected behavior | Users can identify the key record, status, owner and next action without exploratory panning; all secondary fields remain available through an explicit, accessible interaction. |
| Reproduction steps | Open `/clients`, `/cases` or `/admin/settings` at 360×800; inspect the first rows and scrollable area. Compare visible columns with the desktop view. |
| Severity / priority | Medium / P2. The workaround exists, but is hard to discover and increases operational friction. |
| User and business impact | Staff on phones/small tablets can miss identifiers, status or row actions, and may misread a partial row. Dense lists are especially costly for frequent operational work. |
| Root cause | Verified behavior; current tables preserve a desktop-width column model in a narrow content container. Specific implementation ownership needs confirmation per table. |
| Recommended solution / proposed design | Prioritize a small set of columns on mobile and move secondary data/actions into an expandable row or details drawer. Where horizontal scrolling remains, add a visible gradient/scroll hint, preserve the first identifier column, and ensure scrollbars remain usable. Avoid converting every list to cards if that harms scanning density. |
| Acceptance criteria | At 360 px no page-level horizontal overflow; primary identifier/status/action are visible; every column remains reachable by keyboard and touch; row actions have accessible names; table scroll state is visually discoverable; desktop sorting/filtering/export behavior remains intact. |
| Effort | Medium to Large, depending on shared table component coverage. |
| Evidence | Metrics from the 36-capture responsive run and `360-settings.png`, `360-cases.png`, `360-clients.png`. All 72 E2E tests pass for table filters/sort/page/export at the tested browser configuration. |
| Verification status | Verified. |

### UX-003 — Initial JavaScript payload exceeds the configured chunk warning threshold

| Field | Finding |
|---|---|
| Module / screen | Shared frontend loading; production build output. |
| Category / title | Performance and perceived responsiveness — Large initial bundle. |
| Current behavior | `npm run build` succeeds, but Vite warns that the main JavaScript chunk is 1,415.52 kB (reported gzip 433.31 kB), above the configured 900 kB warning threshold. A country-data chunk is also large at 756.54 kB. No slow-network load test was run, so user-visible delay is a risk rather than a measured defect. |
| Expected behavior | Common operational pages load a small initial application shell; map and infrequently used modules load when needed. |
| Reproduction steps | From `src/web`, run `npm run build` and review Vite output. |
| Severity / priority | Medium / P2. |
| User and business impact | On constrained corporate/mobile connections or older devices, first load and page transitions may be slower and memory use higher. This could delay access during operational work. |
| Root cause | Build output verifies chunk size; exact import contributors need bundle analysis before changes. |
| Recommended solution / proposed design | Add route-level lazy loading for less frequent modules and load map/country geometry only on the map route. Inspect dependency duplication and icon imports with a bundle analyzer, then measure cold-load and route-load performance under throttled network/CPU conditions. |
| Acceptance criteria | Initial entry chunk below the agreed budget; map geometry absent from non-map route requests; no interaction regression; measured cold-load LCP/INP within agreed budgets under a documented test profile. |
| Effort | Medium. |
| Evidence | `npm run build` output on audited commit; no field performance data collected. |
| Verification status | Build-size issue verified; user impact suspected and requires performance testing. |

### UX-004 — Small icon and table controls may not meet comfortable touch-target sizing

| Field | Finding |
|---|---|
| Module / screen | Shared shell and table controls; desktop viewport measurements. |
| Category / title | Accessibility and interaction — Some controls measure below 24 CSS px in one dimension. |
| Current behavior | The responsive inspection measured the sidebar collapse button at about 20×20 px; small pagination and row controls were also under 24 px high. Whether each control passes WCAG 2.2 SC 2.5.8 via the spacing exception was not measured. |
| Expected behavior | Pointer and touch targets meet the 24×24 CSS px minimum or clearly satisfy the spacing exception; focus and accessible names are available. |
| Reproduction steps | At desktop width inspect the sidebar collapse control and table pagination/row actions; measure rendered bounding boxes and spacing to adjacent targets. |
| Severity / priority | Low to Medium / P2 pending spacing check. |

| Acceptance criteria | Automated geometry check shows each target meets 24×24 or the documented spacing exception; keyboard focus is visible; touch testing shows no adjacent-action misfires. |
| Effort | Small. |

## F. Quick wins

- Add a narrow-screen active-section menu or visible edge cue to the global navigation.
- Give all icon-only actions explicit accessible names and increase their hit areas.
- Add a “scroll for more columns” hint to narrow table containers until responsive row patterns are implemented.
- Ensure truncated values expose the full value on focus/selection, not hover alone.
- Use route-level lazy imports for the map and large country geometry after bundle analysis.
- Add first-action and retry guidance to empty/error states where the API exposes a recoverable failure.

## G. Strategic UX improvements

- Establish a shared responsive data-table pattern with pinned identifiers, prioritized columns, row detail and consistent filter/export placement.
- Document shell breakpoints and navigation behavior as design-system rules; include keyboard, focus, touch target and reduced-motion requirements.
- Treat role and scope as part of the information architecture: explain why data/actions are absent and provide a clear route to request access where appropriate.
- Add user research before optimizing interaction counts; the application is operationally dense and needs evidence from real task frequency and consequences.
- Consider assisted search and intelligent defaults only where they reduce measurable effort. Suggestions should be explainable, sourced from authorized data, editable before save, and never silently perform approvals or financial actions.

## H. UI/UX modernization opportunities

The existing framework gives the application a coherent base. Modernization should focus on responsive behavior and reusable patterns rather than replacing the visual identity wholesale. Standardize empty/loading/error/success states, narrow table behavior, form validation summaries, focus return after dialogs, and toast lifetime/stack limits. Define design tokens for typography, spacing, color contrast, control height, and state communication. Keep status meaning available in text and not color alone.

## J. Success metrics and baseline plan

No human task-performance baseline exists from this audit. Establish one by observing representative managers, engineers and administrators complete 5–8 common tasks (find a case, update owner/status, create a client/environment, link a contract, export a filtered report, schedule a report, resolve an access issue). Record median and 90th-percentile completion time, task success, errors, backtracks, clicks/keyboard actions and confidence. Repeat with the same scripts after changes.

Proposed targets after baseline collection:

- At least 95% unassisted completion for critical operational tasks.
- Reduce median time for frequent tasks by 20% without increasing errors.
- Reduce avoidable validation/rework errors by 30%.
- Zero confirmed WCAG 2.2 AA critical/high issues in supported core flows; verify with automated and manual methods.
- No page-level horizontal overflow at supported viewport widths; all essential table data reachable and discoverable.
- Keep initial entry JavaScript within an agreed size budget and meet documented cold-load LCP/INP targets on a throttled profile.
- Track support requests and user satisfaction/SUS by role and workflow; set numeric targets only after baseline and sample-size review.

## Test and implementation record

- `dotnet build TioHub.slnx --no-restore`: passed, 0 warnings/errors.
- `dotnet test tests/TioHub.Tests --no-restore` using isolated `(localdb)\TioHubQALocalDB`: **246 passed, 0 failed, 0 skipped**.
- `npx playwright test --list`: 72 tests discovered.
- `npx playwright test` using isolated QA LocalDB and port 5196: **72 passed**.

The initial `(localdb)\MSSQLLocalDB` test run passed 101 tests and failed 145 when SQL connections could not start reliably. `sqllocaldb` reports this instance as Stopped and another start attempt failed. Read-only process/SQL inspection found a SQL Server process (PID 33888, pipe `LOCALDB#11448581`) still serving databases, including an active `TIOHub-Claude` session; the LocalDB registry mapping points at a different process identifier. The process also contains many existing E2E databases. The prior error log records a `TioHub_PortfolioDev.mdf` file-name collision, but the specific cause of the stale LocalDB state is not confirmed. I did not stop or recreate the instance or modify its databases. Instead, I created and used a separate `TioHubQALocalDB` instance for the successful .NET and Playwright runs. This resolves the test-run blocker in an isolated QA environment; it does not repair the original LocalDB registration/process state.

**Files changed:** this audit report only. The temporary responsive Playwright spec used to capture layout evidence was removed after the run. Existing untracked build/test-result directories were present before this report and were preserved.
