# Access control implementation and deployment review

> **Superseded by 2.48.0 (A81).** Kept as a record of earlier releases. Current model: [RIGHTS-MODEL-DESIGN.md](RIGHTS-MODEL-DESIGN.md); administrators: [RIGHTS-ADMIN-GUIDE.md](RIGHTS-ADMIN-GUIDE.md); developers: [RIGHTS-DEVELOPER-GUIDE.md](RIGHTS-DEVELOPER-GUIDE.md).

The access-control overview links to user and role administration, the permission editor and access audit. It also provides a user permission snapshot, direct exception editing, saved-role comparison and a non-executing capability/scope check. Where user administration is visible, the role workspace lists directly assigned users, including inactive accounts; directory group assignments are not included in that list. The check reports **conditional** when its checks pass: a particular business operation can still require other permissions, workflow conditions, ownership or record checks. It does not impersonate the selected user or execute the operation.

## Resolution and boundaries

Active roles contribute a union of registered capabilities. Active direct allows are added and direct denies are removed before the permission dependency graph is resolved. Direct allows are ignored for accounts with the Administration right, including accounts promoted after an allow was assigned; direct denies still apply. This prevents temporary individual access from becoming a source of administrative delegation. An absent prerequisite prevents the dependent capability from becoming effective. Inactive accounts receive no capabilities. User and directory-mapping scopes combine; client, project and internal-team boundaries remain independent of operation permissions. Cross-cutting rights, such as Audit and Export, remain separate required gates. Administrative privileges and overrides for administrators are deliberately managed through roles; direct exceptions cannot edit administration capabilities or the acting administrator's own access. These safeguards are intentionally more restrictive than a complete delegated-administration model.

Exceptions may have a server-enforced expiration. The authorization cache expires no later than the next exception expiry. Changes to access administration, projects and environments advance the database authorization generation transactionally, as do raw-SQL cascade deletions, so subsequent requests re-resolve access and derived project scope. In-flight requests keep their original snapshot. Directory group inspection uses the groups recorded at the user's last authenticated resolution unless the optional Windows live lookup (`Auth:LiveDirectoryLookup`) is enabled, and the inspection states which it used.

Last-observed group snapshots use a versioned encoding that preserves group names containing separators and identifies whether Windows or Development authentication produced them. Older or differently tagged snapshots are unavailable for administrative inspection and delegation until that user signs in again; invalid and oversized snapshots also fail closed. Live sign-in evaluates the authenticated principal's current groups. An inactive Windows user can refresh a snapshot through an authenticated request without gaining application access. Forms identities have no directory groups, so Forms administration can handle inactive accounts without trusting a directory snapshot; a Forms snapshot is not trusted if authentication later changes to Windows. `Directory_snapshot_encoding_round_trips_through_sql_server` covers the SQL Server round trip.

The direct exception editor replaces the selected user's entire exception set in one operation. It requires an ETag from the latest read, validates the submitted set and writes audit records with the changes. It requires an administrator with all active capabilities, because role combinations can otherwise turn a seemingly limited exception into a broader effective grant. An exception can be limited to one client, project or team only for the permissions listed in [SCOPED-PERMISSION-EXCEPTIONS.md](SCOPED-PERMISSION-EXCEPTIONS.md); the API refuses a scope on any other permission and still rejects unrecognized fields. An active account without a role can sign in when it has at least one effective direct permission after dependency and expiry checks; it still needs the relevant scope and separate cross-cutting rights.

Team list and record operations use internal-team scope; creating a team requires all-internal scope. Notifications linked to records require the current permission and a currently visible source record, so a scope revocation also hides the notice. Notifications without a recognized accessible source are not shown.

Reassignment queues and handover candidates show records only when the caller can view the source module. Creating or completing a handover also checks the authorizer's source-module coordination permission and full record scope; an exception requires the acting coordinator's authority as well. Acknowledgment rechecks the original authorizer using their last-observed directory groups, which can be stale. Firewall rule reads and mutations require both endpoint servers to be visible and server View permission; technical-detail and operation permissions still apply.

For project-only access to a client case, the case must have an affected environment and every linked environment, asset and component must be within the user's project scope; a linked contract must also belong to an authorized project. This conservative rule prevents a case shared with an inaccessible project from disclosing its narrative and history. Project-only access to an organization's parent client exposes its name and alias but masks client-wide organization details. Contract penalty assessments require full client scope because they may contain identities of cases outside the current project.

Project-scoped commitments and escalations also require their linked cases to be visible; escalations require linked contracts to be visible. Attachment mutations resolve the current target rather than relying only on the scope recorded when the file was uploaded. Inventory cloning requires permission to read the source details. Export history hides sensitive metadata when the original access fingerprint no longer matches, and queued user exports are refused if access changes before processing.

Manual data-quality scans now require global client and internal scope because they modify records globally. Client duplicate lookup requires client-create permission and global client scope. To avoid revealing hidden Jira reuse, every newly linked Jira reference requires a reason, and the reuse lookup returns only visible matches; API clients that previously omitted the reason must be updated. Project and contract views hide related products and environments when the corresponding View permission is absent; saves preserve those hidden relationships. Creating a note link requires permission to read the linked client or project. Previously copied personal-note labels remain stored snapshots.

Scheduled exports do not have an authenticated directory principal. They use direct roles and scopes, and refuse to run when any possible mapped role combination could violate an incompatible-role policy or suppress a direct allow. This can refuse legitimate schedules until authoritative directory membership is available.

Forms password issuance and resets require an administrator with all active permissions, cross-cutting rights, and global client and internal scope. The endpoint rejects accounts holding an administrative role, including an inactive administrative role; an administrator's own password is changed through the normal password-change flow. An account must receive its initial password before being promoted to an administrative role. Resetting an existing administrator's lost password requires an approved recovery process. Forms recovery checks require an active account with a structurally usable password hash and effective management permissions; they cannot establish that the owner knows the password.

The password dialog checks reset availability against the same server-side rules before allowing submission, and the server checks again when the password is submitted. Forms setup detection also looks for an active account with effective user-administration permissions and a structurally usable credential; a disabled role, denied permission, inactive account or malformed credential alone does not suppress setup. Setup checks that provisioning leaves an effective administrator before committing and consuming the one-time code. This recovery path still requires isolated database testing; disabled permission definitions or an invalid conflict policy can require an out-of-band repair.

Administrators can configure incompatible role pairs in the access-control workspace. The policy is opt-in: no pairs are enforced until configured. The server checks active direct roles and directory-mapped roles together, refuses known conflicting assignments, and denies access if a conflict appears later. Enabling a policy requires an active recovery account with only the protected Manager role directly assigned and effective permission to maintain roles after direct denies and prerequisites; user administration protects that recovery account while the policy is active. Directory mappings currently add only the Manager or Engineer built-in roles, and the protected Manager role cannot be included in a pair. Revisit the recovery invariant if mappings are extended to arbitrary roles. Policy edits are audited and use optimistic concurrency. A malformed stored policy or an out-of-band registry change that removes recovery permissions requires an out-of-band, audited repair.

Deleting any client record requires full client scope, because project visibility alone does not authorize changes to the whole record. Cascade previews and deletes read every client and team reached by the rows they would delete or unlink, and proceed only when all of them lie in the caller's full data scope; one row outside it gives the same answer as a missing record.

## Data scope and upgrade

Before any deployment, review [the scope migration and recovery procedure](AUTHORIZATION-DATA-SCOPE-UPGRADE.md), the complete generated deployment SQL and every migration. `20261102120000_PreserveLegacyEffectiveScopes` makes the previous broad role visibility explicit for existing active-role holders and existing role-backed group mappings. Existing mappings can consequently grant broad scope to their future members until an administrator narrows them. New users and mappings start without data scope. The preserved prior flags and audit entries are review aids, not an automatic rollback script.

`20261102120037_UserPermissionOverrides` adds the exception table. `20261102140000_ExportAccessFingerprint` adds an access fingerprint to generated report files. New exports capture their effective access before reading report rows; downloads reject a file when current access differs. Older files have no fingerprint and must be regenerated. The fingerprint does not make report data immutable and does not replace query and resource authorization.

The migration scripts have been prepared for DBA review; they have **not** been applied or validated against a database in this work. Production startup migrations remain disabled. Take the documented backup, test migration and rollback on an approved isolated copy, review compatibility grants, then use the approved DBA deployment process. Rolling application code back restores legacy scope behavior and does not preserve the newer restrictions.

## Remaining acceptance work

The endpoint audit and its open items are in [AUTHORIZATION-AUDIT-2.45.md](AUTHORIZATION-AUDIT-2.45.md). Read permissions cannot yet carry a scope. Incompatible role pairs do not enforce workflow-level separation of duties; A75 in [DECISIONS.md](DECISIONS.md) records why no approval workflow was added and the owner decision it leaves open. Last-administrator checks in every mode now prove effective permissions, through last-observed groups in directory modes unless the optional live lookup is configured. That lookup has not been run against a real domain. Legacy cross-cutting rights still coexist with granular capabilities. Some operations must disclose that a conflicting record or dependency exists to prevent unsafe changes, even when details are not visible. The access check intentionally cannot guarantee a specific operation will succeed. What has actually been verified is in [RELEASE-VALIDATION-2.45.0.md](RELEASE-VALIDATION-2.45.0.md).
