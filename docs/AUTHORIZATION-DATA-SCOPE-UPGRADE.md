# Data scope upgrade and recovery

> **Superseded by 2.48.0 (A81).** Kept as a record of earlier releases. Current model: [RIGHTS-MODEL-DESIGN.md](RIGHTS-MODEL-DESIGN.md); administrators: [RIGHTS-ADMIN-GUIDE.md](RIGHTS-ADMIN-GUIDE.md); developers: [RIGHTS-DEVELOPER-GUIDE.md](RIGHTS-DEVELOPER-GUIDE.md).

The application enforces the saved all-client, client, project, all-internal and team scopes as mandatory data boundaries. New users and new group mappings have no data scope unless one is explicitly assigned. A user's direct scope and the scopes of their matching directory groups combine; operation permissions are also required. Delegated administrators can assign only scopes that they hold themselves. The server-local one-time Forms setup and configured initial Windows bootstrap establish explicit all-client and all-internal scope for the recovery administrator.

The `20261102120000_PreserveLegacyEffectiveScopes` migration preserves the previous effective behavior, in which any active role gave visibility to all clients and internal teams. It sets both flags on every existing account with an active directly assigned role, including inactive accounts that might later be reactivated. It also sets both flags on every existing mapping backed by an active built-in role, preserving the former behavior for group-only users. Future members of those existing mappings inherit the saved broad scope; review and narrow the mappings after deployment when appropriate. Previously configured narrower scopes remain in place but cannot narrow an all-scope grant until that flag is removed.

Before deployment, take the normal full backup and have the DBA review the complete regenerated `database/01-schema.sql` and all three new migrations. Apply only through the approved deployment procedure. Verify recovery administrator access, scope changes and revocation, mapped users, representative client/project/team records, handovers, reports and exports in an isolated restored copy first. Review the access audit entries with action `PreserveLegacyScope` and plan staged reductions of inherited broad grants. Do not deploy the application before its required migrations.

The migration saves previous flags in `iam.LegacyScopeUpgrade` and records an audit entry for each migrated account or mapping. The backup describes stored flags, not the old effective access; it is reference material for a DBA and must not be applied blindly. The migration's down operation intentionally leaves both the snapshot and current flags in place, because automatic restoration could erase access changes made after upgrade. Rolling back the application restores its former broad role behavior and therefore does not enforce narrowed scopes. For database recovery, follow the backup/restore process in `OPERATIONS.md`, assess changes made since backup, and reconcile them before switching. If individual stored flags need restoration, compare the snapshot with current assignments and audit history and apply only an approved, reviewed correction; never bulk overwrite subsequent changes.

Handover records may contain multiple clients and internal items. A handover is visible only when all its items are within the viewer's scope. Internal handover items have no stored team identifier, so they require all-internal scope; this conservative restriction avoids exposing another team's work. Project-scoped users can see a limited client summary and the client overview shows only names and codes of regions used by their visible environments, without region owners. Client-wide region details and client/region attachments require full client scope. Some other environment views may omit region labels for project-only users.
