# Business accuracy — stage 2

Scope: correct penalty and SLA calculations, inventory copy classification, and operational transition validation. Resource permissions and deployment readiness from stage 1 remain in place. Reporting/configuration improvements and the unapproved policy changes identified in the review are separate work.

## Penalty assessments and historical terms

- A clause's calculation terms determine its cohort; unrelated clauses and descriptive label edits must not split its monthly cap.
- Genuine changes to financial terms retain the cases' recorded terms as distinct cohorts. The hub does not invent a retroactive amendment or a cross-version accounting settlement. Mixed amended terms remain subject to review.
- Recalculation reconciles persisted assessments, including keys generated by older application versions. Obsolete charges are retained as zeroed/superseded history, with confirmation cleared, rather than remaining active charges or being silently deleted.
- Changed underlying breach populations require review even if the capped amount is unchanged. An unchanged recalculation preserves confirmation.
- Priority changes continue to refresh SLA targets under A61, but retain their existing penalty snapshot under A63. The existing unlink-then-link workflow deliberately takes current penalty terms; sending the same contract ID remains rejected.
- Recalculation and confirmation serialize per contract. Penalties remain indicative and never issue credits or invoices. Case previews show monthly totals for cases sharing the recorded clause terms; the same total can appear on several case pages and must not be added together.
- Assessment rows show their recorded calculation rate and cap, including historical terms after an amendment. Recalculation remains available for existing assessments even after the live clauses are removed. API validation failures are displayed in the assessment panel.
- The existing assessment breach-identity column has a 4,000-character limit. An oversized calculation returns a controlled validation error before changing any assessment; extending that capacity requires a separate reviewed schema change.

## Overnight SLA calendars

A support window with an end time before its start ends on the next local day and belongs to the selected starting support day. Its previous-day tail can count toward a case opened after midnight. Equal start/end remains incomplete; use the explicit 24x7 option for round-the-clock support.

Calendar boundaries inside a daylight-saving gap advance to the first valid local instant. Repeated boundaries use the earlier instant for the start and later instant for the end; overlapping UTC support intervals count once. These policies apply to calendar boundaries; existing validation for manually entered ambiguous event times is unchanged. Public holidays remain outside the existing calendar model.

The existing SLA sweep also repairs missing deadlines on saved overnight snapshots previously marked Not measurable. It preserves recorded targets, calendars and penalty terms, including historical closed cases. Each sweep repairs up to 500 qualifying cases; keyset traversal skips invalid calendars and targets beyond the calculator's existing 1,500-day horizon so they cannot block later repairable cases. Those uncomputable targets remain Not measurable. Repair runs when the SLA sweep is enabled (five-minute default); this stage does not run it against production.

## Inventory copying

All copy routes preserve both the configured asset type code and its behavior category. Physical hosts remain physical, logical endpoints remain ineligible to host microservices, and provisioning totals use the preserved category. Existing copy permissions, atomicity, lifecycle defaults and provenance rules stay unchanged.

## Operational validation

- Case next action is optional throughout creation, editing, triage, progress and reopening. Required progress, impact, review time and meaningful validation-request information remain enforced.
- Case owner and backup must be different people during ownership transitions.
- Handover completion revalidates the receiving person's activity, business access and applicable record scope. Existing per-item handling for records already changed or unavailable remains explicit.
- Escalation communication/acknowledgement cannot predate receipt. Receipt edits must also respect recorded communications and lifecycle events.

The approved commitment completion restrictions and the informational handover effective date remain unchanged.

## Integration points

Existing API routes are corrected without adding or renaming endpoints:

- `GET /api/v1/cases/{id}/penalty-preview` and contract penalty assessment read/recalculate/confirm routes use matching clause cohorts.
- Existing case triage, assignment, progress, validation and reopen routes retain their contracts while accepting an omitted or blank next action.
- Existing handover acknowledge/exception and escalation update/communication/status routes enforce the additional consistency checks.
- Existing inventory clone routes preserve the asset's behavior category.
